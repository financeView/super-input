## 一、TL;DR（确认发现，按严重度排序）

### 总评

这份调研文档的**原理章（§1-3）质量显著高于典型调研**：[2][3]（微软 TSF / Apple IMK）的全部引用主张经官方原文逐字比对吻合，TSF 三分法、IMK 职责、组合文本机制、拼音 lattice 解码等核心原理描述全部站得住。**§4 WindInput 事实主张逐项核验为真**（MIT/三组件/27 crate/IPC 协议/redb/参考来源，含 CommitThenDeferComposition 0x010C 等源码级细节逐条对应）。

问题集中在两处：**§5 TypeFree 事实层有一组连环错误**（源于「源码私有」的错误前提），以及**§7-8 选型建议章存在系统性盲区**（对「据此动手自研」的支撑不足）。对「自研选型」这一用途，文档可作原理学习底子，但动手前必须补齐下述缺口。

### 重大发现（动摇文档部分结论）

**1. TypeFree「源码私有、无法核验」为连环错误**（三路独立一致确认，A 级一手实测；监工外部抽查复核）
- 文档 L204「无法从公开源码确认其录音设备管理…七项具体实现」、L215「因私有源码不可完全核验」、L278「应用主仓库在公开官网仓库 README 中标注为私有」——前提全部坍塌：`kdsz001/typefree` 公开仓库即含 **macOS App 完整源码**（README「仓库结构」节原文：`mac/` — macOS App 完整源码（Swift，**GPL-3.0**）；89 个 Swift 文件；创建于 2026-06-05）。L204 点名的七项（录音/快捷键/剪贴板回写/API 重试/音频编码/加密存储/错误恢复）全部有对应源文件可核验。`ray-voice` 全仓零出现，疑为文档作者误把 GitHub 仓库描述（只提官网与教程）当成了仓库全貌。
- **选型后果**：TypeFree 路线并非「无参考实现可循」——它本身就是一份覆盖录音→ASR→LLM→粘贴全链路的 GPL-3 参考实现（详见发现 13「未经交叉」）。

**2. L182 供应商描述归属错挂且部分失实**（三路独立一致确认，A 级）
- 「官网公开说明，识别使用火山引擎 BigASR，整理可以在通义千问、智谱 GLM 和豆包之间切换」——官网全站**零出现** BigASR/智谱/GLM；BigASR 是源码内资源 ID（volc.bigasr.auc 等）的产品名；现行设置 UI 仅暴露「通义千问（百炼）/不优化」两档（豆包 2026-09-15 起对新用户隐藏，智谱仅存于配置层无 UI）。减轻情节：L157「识别使用火山引擎」供应商层面是对的，错在「BigASR」产品名与「官网公开说明」归属。

**3. L196「（词条）并配置权重」无依据**（三路独立一致确认，A 级）
- 官网零「权重」表述；源码中权重后缀解析后即丢弃、无任何下游使用；词表实际以无差别上下文句注入。同句「让识别和整理阶段都偏向这些词」为真。

**4. 引用与锚定问题族：[1]（W3C IME API）被系统性高估**（双路独立发现，A/C 级）
- L20 称其为「Web 标准」——实为 2016 年「for history purposes」的历史性 Working Group Note，其独有概念（组合起止位置/候选窗 API）从未在任何主流浏览器实现（MDN 无条目）；composition 真正载体是 UI Events（仍为 WD）。
- L8 摘要句「Windows 通过 TSF…macOS 通过 IMK…[1] [2]」——[1] 为纯 Web 规范，零桌面内容，不支撑该句任何主张；macOS 半句的正确引用 [3] 未挂（文档 L36/L76 处曾正确挂载过，属漏挂而非不知）。
- **对文档核心论断的影响**：不动摇「桌面 IME 应经系统文本服务接口报告组合/提交」（该论断经 TSF 官方文档独立证实），但引用规范度有系统性缺陷。

### 选型盲区（C 视角发现，两路独立确认）

**5. 「直接基于 librime/libime 二开」替代路径从未被评估**（B 级，对选型影响最大）
- librime=BSD-3（可闭源复用）、libime=LGPL-2.1+（动态链接可保私有壳）、fcitx5-macos 活跃维护证明该路线可产出完整 macOS IME。若目标是「产可用产品」而非「学习引擎构造」，二开可砍掉 Dictionary/Decoder/Ranker 三个最重模块，工作量级差一个数量级。文档 §7 默认从零自研，该前提未声明。
- **对用户的直接含义**：动手前先回答「我要产品还是要学习」——这一个问题决定走哪条路，而文档没让你意识到要回答它。

**6. 「借鉴」的法律边界全文未界定**（B 级；数据层经 A 路补强）
- 四个参考对象四种边界：WindInput MIT / librime BSD-3 / libime LGPL-2.1+ / Squirrel·Weasel·fcitx5-macos·**TypeFree 全部 GPL-3**（借鉴前端代码=整包 GPL，对闭源分发者是禁手；TypeFree 商标/名称不在许可范围）。数据层独立：WindInput 自己都以 NOTICE.md 声明码表数据（rime-wubi86-jidian/白霜拼音等）适用各自许可。文档全文许可仅 L84 一处描述性提及。

**7. 安装分发/签名零着墨，而这是自研第一天就要面对的硬约束**（B 级；Squirrel release 日期经纠偏为 2026-01-14）
- Windows：TSF IME 是加载进每个应用进程的 DLL（官方「in-proc COM server」），位宽矩阵（x64/x86/arm64，Weasel 有 arm64x_wrapper 实证）是构建分发一等公民。macOS：事实分发形态是 Developer ID 签名+公证的 pkg，未公证会被 Gatekeeper 拦。证书成本、公证流水线、多架构 CI 直接计入 MVP 工作量。App Store 可行性文档未评估（E 级推断）。

**8. §7.1 八模块表缺「进程模型/IPC」，与文档自己的 §4 评价标准不一致**（B 级+文内矛盾）
- 文档 L133-135 把 WindInput 的「显式 IPC 和状态协议」称为输入法领域工程创新（Weasel 四件套为成熟答案），但自己开出的模块清单无对应物——审别人的标准和自己的产出不一致。TSF 壳与引擎同/分进程是动手时的第一个架构决策，文档无据可依。

### 设计观察（两路一致：来源方+确认方，第三路职权外不判断）

**9. v1 功能清单缺翻页**——结论成立（置信升高），机制表述已纠偏：五笔全码重码>10 仅 0.03%（rime-wubi86-jidian 89286 行实测），但 v1 自身定义「前缀候选」——1 码候选>10 的键位 100%、2 码 99%、3 码 17%，**前缀阶段候选溢出为常态**，翻页是 v1 必需。且与 L231 Session 模块已定义「候选页」自相矛盾。

**10. §7.2 状态机纯 happy-path 线性链，工程点与状态机两张皮**——缺 Error/Failed/Cancelled 终态（错误是转移边不是状态属性）、取消/预览无对应态、缺权限预检态（macOS 麦克风 TCC 授权是 onboarding 第一流失点）、漏热键冲突检测。

**11. 核心会话接口输入侧缺「应用文本上下文」通道**——L225 六项输入无 text context，而 L26/L240 自己把它列为平台职责与 v2 能力；v2 上下文解码将要求改接口契约而非只加模块。B 路独立复证含证伪判据检验（「光标位置」是位置信息，不能解释为携带上下文）。

**12. 「整句 AI 会被平台接入拖慢」无论证断言 + MVP 隐含未声明前提**——断言方向与 §3 一致但无机制论证；固定码表 MVP 只在「目标是传统键盘输入法」前提下成立，若用户真实目标是 AI 键盘输入则该路径不适用，文档未声明此前提。

**13.【未经交叉】§7.2 错过公开可得的 GPL-3 参考实现**（C 路 cross 轮新增，B 级一手；事实基础经 U1 三路确认，选型推论部分单路未交叉）
- §7.2 全程「从零推演」口吻，而 typefree 仓库的 mac/ 目录即覆盖其几乎全部工程点的完整参考实现（含钥匙串存储=工程点 6 的参考答案、原剪贴板快照还原=撤销回写的参考答案）。借鉴需守 GPL-3 传染+商标除外边界。

**14. §8 是「研究参考价值」判断而非「构建行动」判断**——缺构建顺序、平台优先级、v1 验收口径；「两者可以组合」隐含双产品工作量翻倍未提示。表述宜为「若报告要支撑选型决策，需补行动层」（B 路定位修正后采纳）。

**15. 工作量/维护成本不可见**（观察级）——v1 一条即含双平台接入+码表+候选 UI+提交，参考对象 WindInput 是 27 crate 三语言项目；无量级信号无法做「自研 vs 二开 vs 用现成」成本对比。

**16. L28「code points」术语混用**（高缺陷判定/低材料性）——Unicode code point 指编码空间整数值，与按键解析产物（编码 token）是两个层面，该行应为 key tokens/编码序列。
